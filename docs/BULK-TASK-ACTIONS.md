# Bulk task actions

Inbox and Projects offer **Select tasks**. Select individual visible tasks or up to the first 50 visible tasks, then complete, move to a nonarchived project/no project, set priority, add a label, or delete. Hidden tasks are removed from selection; newly visible tasks are never selected automatically. Leaving selection mode clears it. Keyboard users can focus a checkbox and press Space.

Each selection captures the saved task and version. Background refreshes never silently rebase that selection, including when selecting visible tasks again. Writes run sequentially through existing owner/version-checked APIs, not an atomic batch transaction. Other saving controls remain disabled through the batch and final refresh. Successful tasks are deselected. Each result reports saved or not confirmed; a lost response is never retried automatically. Reload and review unconfirmed tasks before selecting fresh versions. A failed final refresh does not turn confirmed writes into failed writes.

Only the chosen property changes. Exact deadlines, work blocks, reminder timestamps, descriptions and parent relationships are preserved. Recurrence and edit scope are omitted, retaining existing occurrence exceptions/future defaults. Completing a recurring task uses the existing successor-generation model. Completing focus tasks also updates daily focus; a failed focus update is disclosed separately. No eager occurrences or bulk rescheduling are introduced.

Project moves do not silently detach subtasks or cascade to children. Existing hierarchy restrictions can reject a move; the rejection appears in per-task results. Deletion requires a count-based confirmation and uses each task's existing deletion-Undo endpoint, never permanent deletion as a fallback. Tasks with subtasks still obey server guards; deletion is not a recursive operation. Every confirmed deletion has its own short-lived Undo receipt, including removal of existing linked content according to normal task deletion rules.

Account changes stop subsequent writes and discard old-account results. In-flight server writes cannot be cancelled or rolled back by closing a view; the store retains batch results while navigation occurs. A workspace reload recovers active deletion receipts as usual. Provider synchronization remains asynchronous; a saved task is not proof of an applied Google change.

Tests cover sequential version-bound writes, partial results, held busy state, account changes, confirmed-save/failed-refresh distinctions, Undo receipts, unchanged scheduling/recurrence payloads, selection limits/filter pruning, keyboard selection, confirmations, desktop/mobile and 320px light/dark layouts. A real-backend browser scenario uses normal session cookies/CSRF, changes priority/project/status, deletes and restores one task, and cleans up with current versions. No live Google account writes are required.
